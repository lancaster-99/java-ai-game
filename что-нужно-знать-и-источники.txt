============================================================
1. ГЛАВНАЯ МОДЕЛЬ ПРОЕКТА — ПОНЯТЬ ДО НАПИСАНИЯ НОВОГО КОДА
============================================================

ЧТО ТЫ СТРОИШЬ

Не «нейросеть, которая программирует игру», а систему из двух частей:

1. LLM преобразует естественный запрос игрока в ограниченный JSON.
2. Обычный Java-код проверяет JSON и строит режим из заранее реализованных
   игровых механик.

Цепочка:

запрос игрока
-> prompt
-> текстовый ответ Phi
-> извлечение JSON
-> Jackson parse
-> GameModeSpecValidator
-> GameModeSpec.normalize()
-> GameModeApplier
-> игровые объекты и правила
-> update(tpf)
-> победа/поражение
-> cleanup.

ЧТО НУЖНО УМЕТЬ ОБЪЯСНИТЬ

- Почему LLM не получает прямой доступ к rootNode, физике и файлам.
- Почему поддерживаемые режимы ограничены шаблонами.
- Чем GameModeSpec отличается от реального игрового состояния.
- Почему наличие поля в JSON ещё не означает реализованную механику.
- Почему ошибка модели не должна приводить к падению игры.

GameModeSpec — это DTO, объект переноса данных. Он описывает желаемый режим.
GameSession/ObjectiveController/списки активных врагов — это уже состояние
работающей игры. Не смешивай эти две вещи.

Граница возможностей:
Если игра умеет survive и collect, LLM может выбирать параметры только этих
механик. Просьба «сделай гонку» не создаёт гонку волшебным образом. Сначала
Java-механика и тест, затем новое значение в схеме и prompt.

============================================================
2. JAVA — МИНИМУМ, КОТОРЫЙ ДЕЙСТВИТЕЛЬНО ИСПОЛЬЗУЕТСЯ
============================================================

2.1. КЛАССЫ, ИНТЕРФЕЙСЫ И ЗАВИСИМОСТИ

Нужно понимать:
- класс, объект, поле, метод, конструктор;
- static и экземплярные члены;
- public/private/package-private;
- наследование на примере Main extends SimpleApplication;
- implements на примере OnnxGenAiPhiClient implements LocalLlmClient;
- композицию: GameModeGenerator получает LocalLlmClient через конструктор;
- @Override и проверку сигнатуры компилятором;
- исключения checked/unchecked хотя бы на уровне обработки в текущем коде.

Зачем интерфейс LocalLlmClient:
Main и GameModeGenerator не должны зависеть от конкретной Phi. Один интерфейс
позволяет подставить реальную модель, Mock или тестовый клиент с заранее
заданными ответами.

Практический признак понимания:
Ты можешь создать FakeLlmClient implements LocalLlmClient и вернуть из него
три заранее заданных ответа, не меняя GameModeGenerator.

Не нужно сейчас:
- сложные иерархии наследования;
- рефлексия;
- собственные annotations;
- паттерны ради паттернов;
- Spring и dependency injection framework.

2.2. КОЛЛЕКЦИИ И РАБОТА С ДАННЫМИ

Нужно знать:
- List для упорядоченных spawns/rules/активных сущностей;
- ArrayList и безопасное создание пустого списка вместо null;
- Set.of(...) для белого списка допустимых строк;
- Map<String, String> для будущего соответствия типа модели пути;
- перебор for-each;
- removeIf для удаления недопустимых элементов;
- почему нельзя бездумно удалять элементы из списка во время его for-each;
- String.isBlank(), trim(), formatted(), text blocks Java;
- массив float[] position ровно из трёх координат;
- Locale.ROOT при приведении технических значений к нижнему регистру.

Активные сущности удобно хранить отдельно:
- активные враги;
- активные предметы;
- физические тела;
- отложенные действия;
- зарегистрированные listeners.

Это нужно не только для update, но и для гарантированной очистки.

2.3. ЧИСЛА, NULL И ЗАЩИТНЫЕ ПРОВЕРКИ

Нужно понимать:
- int для счёта, секунд и здоровья;
- float для координат, скорости и tpf;
- переполнение и слишком большие значения;
- NaN и Infinity;
- почему обычный clamp через Math.min/Math.max не делает NaN безопасным;
- Float.isFinite(value) до применения числа;
- null-проверки на границе недоверенных данных.

Важный пример текущего риска:
normalize() ограничивает числа, но NaN может пройти через сравнения и дальше
испортить координаты/движение. Поэтому валидатор должен проверять конечность,
а нормализация — подставлять безопасное значение.

2.4. ИСКЛЮЧЕНИЯ И ЛОГИРОВАНИЕ

Нужно уметь:
- отличить ошибку загрузки модели от ошибки генерации и от ошибки apply;
- сохранять первопричину исключения;
- печатать полный stack trace в лог;
- показывать игроку короткое понятное сообщение;
- не проглатывать важные ошибки пустым catch;
- не показывать пользователю огромный stack trace в HUD.

Полезный порядок диагностики:
1. Найти первое исключение.
2. Найти его caused by.
3. Найти первую строку своего кода в stack trace.
4. Воспроизвести ошибку одним минимальным действием.
5. Только после этого менять код.

============================================================
3. МНОГОПОТОЧНОСТЬ — ОДНА ИЗ КЛЮЧЕВЫХ ТЕМ КУРСОВОЙ
============================================================

3.1. ЧТО ТАКОЕ RENDER-ПОТОК

jME выполняет игровой цикл и обновление сцены в своём update/render-потоке.
В simpleUpdate(tpf), Control.update() и AppState.update() обычные игровые
изменения выполняются в правильном контексте.

Долгая операция в этом потоке останавливает кадры:
- generate() может занимать секунды;
- загрузка модели тоже тяжёлая;
- Future.get()/ожидание результата в simpleUpdate снова создаст фриз;
- Thread.sleep() для игровых таймеров блокирует игру.

3.2. КАК РАЗДЕЛЕНА РАБОТА В Main

llmExecutor — однопоточный ExecutorService:
- загружает модель;
- выполняет generate();
- не даёт двум тяжёлым генерациям идти одновременно.

CompletableFuture:
- supplyAsync запускает генерацию;
- whenComplete получает результат или ошибку;
- callback не становится автоматически render-потоком.

enqueue(...):
- возвращает применение результата в поток jME;
- там можно менять rootNode, guiNode, controls, input и physics.

Правило:

ФОН: LLM, тяжёлые вычисления, измерение генерации.
RENDER: сцена, HUD, input mappings, physics, создание/удаление Spatial.

3.3. СОСТОЯНИЕ И ВИДИМОСТЬ ПЕРЕМЕННЫХ

volatile обеспечивает видимость изменения между потоками, но не превращает
последовательность «проверить -> установить» в одну атомарную операцию.

В текущем Main startGeneration вызывается из обработчика ввода jME, поэтому
проверка generating и установка флага концентрируются в одном потоке. Если
позже запускать генерацию из нескольких потоков, понадобится единый владелец
состояния или AtomicBoolean.compareAndSet(false, true).

Обязательные свойства:
- generating устанавливается до отправки задачи;
- сбрасывается и при успехе, и при ошибке;
- modelReady не выставляется до полной загрузки;
- модель не закрывается во время активной генерации;
- executor останавливается при destroy();
- нативные ресурсы клиента закрываются.

3.4. ИГРОВОЕ ВРЕМЯ БЕЗ ПОТОКОВ

Таймеры, cooldown и задержки обновляются через tpf:

remainingSec -= tpf;
attackCooldown -= tpf;

tpf — время предыдущего кадра в секундах.
Не создавать поток на врага и не использовать Thread.sleep() для респауна.

ЧТО НУЖНО УМЕТЬ ДОКАЗАТЬ НА ДЕМО
Во время «NPC думает…» окно продолжает обновляться, игрок/камера не замирают,
а повторная отправка не создаёт параллельную генерацию.

============================================================
4. JSON, JACKSON И GameModeSpec
============================================================

4.1. ЧТО ТАКОЕ JSON ДЛЯ ЭТОГО ПРОЕКТА

Это не исполняемый код, а данные с ограниченной схемой:
- объект: { ... };
- массив: [ ... ];
- строка в двойных кавычках;
- number без кавычек;
- вложенные world/player/objective;
- spawns и rules как массивы объектов.

Нужно уметь вручную прочитать любой пример GameModeSpec и ответить:
- какой режим запрошен;
- сколько групп объектов будет создано;
- какая цель;
- какие параметры игрока;
- какие значения не поддерживаются игрой.

4.2. OBJECTMAPPER

ObjectMapper.readValue(json, GameModeSpec.class):
1. Разбирает JSON.
2. Создаёт DTO и вложенные объекты.
3. Заполняет public-поля.
4. Выбрасывает исключение при несовместимом содержимом.

Текущие настройки:
- FAIL_ON_UNKNOWN_PROPERTIES отключён: неизвестные поля игнорируются;
- ALLOW_TRAILING_COMMA включён: висячая запятая прощается.

Это осознанные послабления на границе LLM, а не признак того, что любой ответ
валиден. Смысловую проверку выполняет отдельный Validator.

ObjectMapper настраивай один раз и переиспользуй. Не меняй его конфигурацию
в каждой попытке генерации.

4.3. ЗАЧЕМ ОТДЕЛЬНЫЙ JsonExtractor

Phi может вернуть:
- чистый объект;
- ```json ... ```;
- пояснение до/после JSON;
- обрыв ответа;
- пустой объект;
- вообще не JSON.

Extractor не доказывает валидность. Он только находит кандидата на JSON.
Баланс скобок должен учитывать:
- вложенные объекты;
- строки;
- скобки внутри строк;
- escaped quotes;
- обратные слеши.

После extractor обязателен Jackson. Нельзя считать сбалансированные скобки
достаточной проверкой.

4.4. VALIDATE И NORMALIZE — НЕ ОДНО И ТО ЖЕ

Validate:
- проверяет, можно ли вообще принять ответ;
- обнаруживает {}, пустые обязательные строки, неправильную форму position,
  неизвестный objective, неверные диапазоны, NaN;
- возвращает список понятных ошибок для retry.

Normalize:
- приводит принятую спеку к безопасным значениям;
- ограничивает диапазоны;
- гарантирует non-null секции и списки;
- удаляет неподдерживаемые элементы;
- ограничивает общее количество создаваемых объектов;
- подставляет безопасные значения по умолчанию.

Порядок важен:
parse -> validate -> normalize -> apply.

Если сразу нормализовать мусор, можно случайно превратить бессмысленный ответ
в режим, который выглядит допустимым. Например, {} не должен считаться успешной
генерацией только потому, что normalize способен заполнить дефолты.

4.5. RETRY И FALLBACK

Retry:
- повторный запрос к LLM;
- содержит исходную просьбу и ошибку предыдущего ответа;
- ограничен тремя попытками;
- сам может завершиться ошибкой.

Fallback:
- встроенный Java-режим;
- не обращается к LLM;
- создаётся после исчерпания попыток или при выбранной политике ошибки загрузки;
- явно помечается в HUD как резервный;
- не считается успешным ответом Phi в метриках.

Mock:
- инструмент разработки с детерминированным ответом;
- не fallback и не доказательство работы реальной модели.

Эти три понятия нельзя смешивать на защите.

4.6. PROMPT НЕ ЯВЛЯЕТСЯ ЗАЩИТОЙ

System prompt объясняет желаемый формат, но модель может его нарушить.
Пользовательский текст тоже может содержать «игнорируй схему».
Безопасность обеспечивает не вежливая просьба, а Java-проверки и белые списки.

Prompt должен совпадать с реальными возможностями:
- поддерживаемые enum;
- обязательные поля;
- диапазоны;
- пример при необходимости;
- требование одного JSON без Markdown.

Не добавляй в prompt ball/score/race до реализации соответствующих механик.

============================================================
5. jMONKEYENGINE — ЧТО НУЖНО ДЛЯ СЦЕНЫ И ИГРОВОГО ЦИКЛА
============================================================

5.1. ЖИЗНЕННЫЙ ЦИКЛ SimpleApplication

Нужно знать назначение:
- main()/start() — запуск;
- simpleInitApp() — однократная инициализация;
- simpleUpdate(float tpf) — обновление каждого кадра;
- destroy() — освобождение ресурсов;
- enqueue() — задача обратно в update-поток.

Не создавай каждый кадр новые тяжёлые ресурсы, материалы, модели, шрифты,
executor или physics space без необходимости.

5.2. SCENE GRAPH: Node, Geometry, Spatial

Node — контейнер, Geometry — видимая геометрия с mesh/material,
Spatial — общее понятие объекта сцены.

rootNode — постоянный мир приложения.
modeNode — корень объектов текущего сгенерированного режима.
guiNode — двумерный HUD поверх сцены.

Нужно уметь:
- attachChild/detachChild;
- detachAllChildren;
- setLocalTranslation;
- getLocalTranslation;
- setLocalScale;
- отличать локальные координаты от мировых;
- не хранить единственную ссылку на активную сущность только в scene graph.

detach убирает визуальный объект, но сам по себе не обязан:
- остановить твой игровой цикл;
- очистить список врагов;
- отписать listener;
- удалить физическое тело;
- отменить отложенное действие.

5.3. КООРДИНАТЫ И ВЕКТОРЫ

В jME вертикальная ось — Y.
Vector3f используется для позиции, направления и скорости.

Нужно понимать:
- position.addLocal(direction.mult(speed * tpf));
- normalize перед движением по направлению, чтобы диагональ не была быстрее;
- обнуление Y при преследовании по плоскости;
- distance и distanceSquared;
- ограничение координат границами арены;
- отличие направления игрока от направления камеры.

Для радиуса сбора обычно выгоднее сравнивать distanceSquared с radiusSquared:
не нужен квадратный корень, а смысл проверки тот же.

5.4. ДВИЖЕНИЕ И КАМЕРА

Скорость задаётся в единицах в секунду, поэтому умножается на tpf.
Для WASD храни текущее состояние клавиш, а не перемещай персонажа только
в момент события нажатия.

Минимальный PlayerController должен разделять:
- настройки из spec: moveSpeed/jumpForce/maxHealth;
- текущее состояние: health/position/enabled;
- update(tpf);
- reset()/damage();
- ограничения арены.

Камера следования обновляется после перемещения игрока.
Для MVP достаточно стабильного смещения и lookAt; плавность не обязательна.

5.5. INPUT

Нужно различать:
- KeyTrigger — клавиша;
- mapping — логическое имя действия;
- ActionListener — дискретное нажатие/отпускание;
- AnalogListener — непрерывное действие, если выбран такой подход;
- isPressed — не обрабатывать отпускание как второе нажатие.

При открытии TextField:
- игровое движение отключается;
- E/Escape не должны конфликтовать с редактированием;
- Enter отправляет только один запрос;
- пустой запрос не отправляется;
- повторная отправка блокируется generating;
- после закрытия управление возвращается.

Лучше иметь явное состояние EXPLORING/DIALOGUE/GENERATING, чем разбросанные
несогласованные boolean-флаги по разным классам.

5.6. NPC И ВЗАИМОДЕЙСТВИЕ

NPC для MVP — Spatial с фиксированной позицией.
Каждый кадр проверяется расстояние до игрока:
- вне радиуса — подсказки нет;
- внутри радиуса — «E — поговорить»;
- нажатие E открывает ввод один раз.

NPC не обязан быть физическим персонажем или иметь собственный AI.
Его роль — понятная точка входа в генерацию.

5.7. HUD И LEMUR

BitmapText подходит для вывода:
- модель загружается/готова/ошибка;
- NPC думает;
- название режима;
- цель;
- здоровье;
- счёт;
- оставшееся время;
- победа/поражение/fallback.

HUD обновляется в render-потоке. Не пересоздавай все тексты каждый кадр:
создай элементы один раз и меняй setText().

BitmapText сам по себе не является полноценным редактором ввода.
Для TextField планируется Lemur:
- GuiGlobals.initialize(app) один раз;
- панель и TextField создаются централизованно;
- фокус и видимость управляются состоянием диалога;
- слушатели не добавляются повторно при каждом открытии;
- панель корректно скрывается/удаляется.

Версию Lemur фиксируй в pom после проверки совместимости и компиляции.
Не копируй версию из случайного примера как гарантированно подходящую.

5.8. МАТЕРИАЛЫ, СВЕТ И ПОГОДА

Unshaded-материал показывает цвет без освещения.
Освещаемые и PBR/glTF-материалы требуют света.

WorldApplier должен владеть изменяемыми эффектами:
- DirectionalLight;
- AmbientLight;
- цвет фона;
- fog/rain preset;
- FilterPostProcessor, если он используется.

Для day/night/sunset достаточно трёх проверенных пресетов.
Для fog/rain в MVP достаточно простого повторяемого эффекта.
Переиспользуй processor/filter и не добавляй новый при каждом режиме.

============================================================
6. ИГРОВЫЕ МЕХАНИКИ И СОСТОЯНИЕ РЕЖИМА
============================================================

6.1. КОНЕЧНЫЙ АВТОМАТ СОСТОЯНИЙ

Минимум:

READY -> RUNNING -> WON
                 -> LOST

После WON/LOST:
- враги прекращают движение и урон;
- таймер не продолжает менять результат;
- сбор предметов не меняет итог;
- завершение выполняется только один раз;
- HUD показывает результат.

Метод finish(result) должен быть устойчив к повторному вызову:
если состояние уже WON/LOST, повторно ничего не делать.

6.2. SURVIVAL

Нужно понимать и реализовать:
- преследование по плоскости;
- speed * tpf;
- дистанцию атаки;
- cooldown;
- damage;
- health не ниже нуля;
- смерть один раз;
- победу по таймеру;
- поражение по здоровью;
- сброс при повторном запуске.

Не нужно для MVP:
- pathfinding;
- NavMesh;
- сложные анимации;
- отдельные потоки врагов;
- боевой ИИ с конечным автоматом из множества состояний.

6.3. COLLECT

Для каждого предмета:
- active;
- spatial;
- позиция;
- pickupRadius.

При касании:
1. Проверить RUNNING и active.
2. Сразу active = false.
3. Удалить spatial.
4. Увеличить счёт ровно на один.
5. Обновить HUD.
6. Проверить targetCount.

Победа: score >= targetCount.
Поражение: истёк лимит, если цель не выполнена.

6.4. FOOTBALL

Минимальная честная формулировка:
«Игрок должен забить N голов за ограниченное время»,
а не «полноценный футбол с AI-соперниками».

Нужно понимать:
- динамическое тело мяча имеет массу > 0;
- статическое тело пола обычно имеет массу 0;
- RigidBodyControl добавляется и в Spatial, и в PhysicsSpace;
- при cleanup одного detach недостаточно;
- после гола сбрасываются позиция, линейная и угловая скорости;
- нужна защита от повторного засчитывания одного эпизода;
- гол можно определять простой геометрической областью ворот.

Bullet подключается только на соответствующем этапе.
Если простой контроллер мяча выбран вместо Bullet, его ограничения нужно честно
описать; не называть его полноценной физической симуляцией.

6.5. OBJECTIVECONTROLLER И RULEENGINE

ObjectiveController отвечает за текущую цель, счёт, время и результат.
RuleEngine реагирует только на реально реализованные события и действия.

Не обязательно сразу поддерживать всё из GameModeSpec.rules.
Если действие ещё не реализовано, нельзя утверждать, что оно работает только
потому, что строка есть в JSON.

Для MVP можно реализовать базовые win/lose напрямую, а RuleEngine расширять
маленькими частями после стабильного игрового цикла.

6.6. CLEANUP — ОБЯЗАТЕЛЬНАЯ МЕХАНИКА

Перед новым режимом:
1. Остановить старый GameSession.
2. Отменить отложенные действия и таймеры.
3. Удалить physics bodies/controls/listeners, если они есть.
4. Отписать input/UI listeners, созданные режимом.
5. Очистить списки активных entity.
6. Очистить modeNode.
7. Сбросить погоду и временные эффекты.
8. Сбросить HUD и ссылки на старый режим.
9. Только затем применить новую спеку.

Проверка: 20 переключений подряд без роста объектов, старого урона,
двойных слушателей и старых физических тел.

============================================================
7. ONNX RUNTIME GENAI И PHI — ЧТО ПРОИСХОДИТ В КЛИЕНТЕ
============================================================

7.1. ЗАЧЕМ ONNX RUNTIME GENAI

Задача проекта — инференс уже готовой LLM, а не обучение сети.
GenAI-библиотека предоставляет высокоуровневый цикл генерации:
- загрузку модели;
- токенизацию;
- генератор;
- параметры поиска;
- последовательное создание токенов.

DL4J для этой конкретной цепочки не нужен. Не требуется самостоятельно
реализовывать архитектуру Phi, attention, KV-cache или обучение.

7.2. ОСНОВНЫЕ ОБЪЕКТЫ OnnxGenAiPhiClient

Model:
- загружается из каталога модели;
- тяжёлый нативный ресурс;
- создаётся один раз;
- закрывается в close().

Tokenizer:
- encode(prompt) превращает текст в токены;
- создаёт TokenizerStream для декодирования результата;
- закрывается при завершении клиента.

GeneratorParams:
- параметры конкретной генерации;
- AutoCloseable;
- max_length в текущем коде = promptTokens.length + newTokensLimit.

Generator:
- получает токены prompt через appendTokens;
- generateNextToken() выполняет шаг генерации;
- isDone() означает завершение по EOS/условию остановки/лимиту;
- AutoCloseable.

TokenizerStream:
- декодирует новые токены в фрагменты текста;
- один видимый фрагмент не обязан быть отдельным словом;
- AutoCloseable.

7.3. ТОКЕНЫ И ЛИМИТЫ

Токен — не символ и не обязательно слово.
maxNewTokens = 768 ограничивает новую часть ответа через расчёт max_length.
Слишком маленький лимит может обрезать JSON до закрывающей скобки.
Слишком большой увеличивает максимальное время и объём ненужного ответа.

temperature = 0 в текущем клиенте означает ветку do_sample=false,
то есть жадный/deterministic режим вместо sampling.
Это повышает повторяемость, но не гарантирует правильный JSON.

7.4. CHAT TEMPLATE

Phi instruct ожидает диалоговый формат, а текущий GameModeGenerator использует
роли <|system|>, <|user|>, <|assistant|> и <|end|>.

Нужно уметь показать:
- где системная схема;
- где исходный запрос;
- где начинается ответ assistant;
- почему служебные токены удаляются из результата;
- почему retry сохраняет исходный запрос, а не подменяет его текстом ошибки.

Не меняй шаблон, модель и параметры одновременно: иначе не поймёшь, что помогло.

7.5. НАТИВНЫЕ РЕСУРСЫ И ЗАГРУЗКА

Проверь:
- каталог модели существует;
- genai_config.json находится именно в нём;
- используется совместимый набор Java/native зависимостей;
- архитектура JDK и нативных библиотек совпадает;
- модель не загружается повторно на каждый запрос;
- Generator/Params/Stream закрываются после каждой генерации;
- Model/Tokenizer закрываются при завершении приложения.

Не скачивай случайные DLL со сторонних сайтов. Сначала сохрани полный
UnsatisfiedLinkError/GenAIException и проверяй официальные артефакты и версии.

7.6. ЧТО СЧИТАЕТСЯ ПОДТВЕРЖДЕНИЕМ РАБОТЫ PHI

Недостаточно: «класс OnnxGenAiPhiClient написан».
Нужно фактически:
1. Запустить OnnxSmokeTest.
2. Получить ответ.
3. Запустить Main с -Dgameai.llm=onnx.
4. Отправить запрос через игровой pipeline.
5. Увидеть валидированный режим или корректный retry/fallback.

10. МЕТРИКИ — КАК ПОЛУЧИТЬ ЧЕСТНЫЕ ЦИФРЫ
============================================================

Измерять отдельно:
- холодную загрузку Model/Tokenizer;
- каждую попытку генерации;
- полный request до валидной спеки;
- parse/validation;
- apply;
- generatedTokens;
- tokens/sec;
- успех с 1/2 попытки при текущем MAX_ATTEMPTS = 2;
- fallback;
- примерный общий RAM процесса.

System.nanoTime() подходит для длительности операций.
generationMs не смешивать с modelLoadMs.

generatedTokens можно считать по числу выполненных generateNextToken()
в конкретной попытке. Не считать callbacks onPiece токенами.

tokensPerSec = generatedTokens / (generationTimeMs / 1000.0).

JSON success rate:
число запросов, завершившихся валидной спекой от LLM / все запросы.
Fallback отдельно не считать успешным ответом LLM.

Fallback rate:
число запросов с fallback / все запросы.

Для отчёта полезны среднее и медиана, но при малом наборе достаточно среднего
с явным указанием числа запусков и аппаратной конфигурации.

Память нативной модели не сводится к Java heap. Используй диспетчер задач
или внешний профилировщик и записывай, как именно получена цифра.

Набор запросов должен включать не только удачные демо:
- survival;
- collect;
- football;
- неполный запрос;
- противоречивый;
- неподдерживаемая механика;
- экстремальные параметры;
- требование текста вместо JSON;
- повтор одного запроса.

11. TROUBLESHOOTING — КАК ДУМАТЬ ПРИ ОШИБКАХ
============================================================

СИМПТОМ: не найден genai_config.json.
Проверить: абсолютный phi.model.dir, содержимое каталога, кавычки пути.
Не делать: переписывать генератор.

СИМПТОМ: UnsatisfiedLinkError / нативная DLL не загружается.
Проверить: полный stack trace, точные версии артефактов, x64 JDK,
совместимость пакета и нативных зависимостей, отсутствие случайных старых DLL.
Не делать: массово менять все версии одновременно.

СИМПТОМ: не хватает памяти.
Проверить: не создано ли несколько Model, размер модели, RAM процесса,
закрываются ли ресурсы, не идут ли генерации параллельно.
Уменьшение maxNewTokens не заменяет исправление повторной загрузки модели.

СИМПТОМ: Phi возвращает обрыв JSON.
Проверить: сырой ответ, достигнут ли лимит токенов, длину prompt, retry.
Затем validator/fallback. Не пытаться применить обрыв.

СИМПТОМ: Phi возвращает Markdown/пояснения.
Проверить: extractor, strict prompt, temperature/do_sample, тесты.
Markdown сам по себе не является провалом, если JSON корректно извлечён
и провалидирован.

СИМПТОМ: игра зависает при генерации.
Проверить: где вызван generate/load, нет ли Future.get()/join()/sleep()
в render-потоке, не выполняется ли apply слишком тяжёлой операцией каждый кадр.

СИМПТОМ: игрок двигается во время набора текста.
Проверить: состояние DIALOGUE, enabled PlayerController, конфликт mappings,
обработку Enter/E.

СИМПТОМ: старые враги атакуют после смены режима.
Проверить: старый GameSession остановлен, списки очищены, controls/listeners
удалены, update не держит старую ссылку.

СИМПТОМ: мяч остаётся после football.
Проверить: PhysicsSpace.remove(...), удаление control/listener, очистку ссылок,
а не только detachAllChildren().

СИМПТОМ: тесты не запускаются Maven.
Проверить: src/test/java, имя *Test, JUnit 5 dependency, современный Surefire,
реальный вывод Maven, отсутствие -DskipTests.

СИМПТОМ: NaN портит сцену.
Проверить: Float.isFinite в Validator/normalize до apply, лог сырого JSON.

СИМПТОМ: glTF/GLB чёрный.
Проверить: DirectionalLight/AmbientLight и материал. Но GLB не является
приоритетом до стабильного MVP.

12. ЧТО НУЖНО УМЕТЬ ОБЪЯСНИТЬ НА ЗАЩИТЕ
============================================================

Короткие ответы должны быть готовы по пунктам:

1. Почему локальная модель:
   работа без сети и внешнего API, приватность запроса, воспроизводимый локальный
   эксперимент; цена — память, скорость и зависимость от native runtime.

2. Почему ONNX Runtime GenAI, а не DL4J:
   нужен готовый генеративный инференс Phi, а не обучение собственной сети.

3. Что генерирует нейросеть:
   только параметры ограниченной JSON-спецификации, не Java-код и не команды движка.

4. Почему ответ недоверенный:
   языковая модель вероятностно создаёт текст и не гарантирует схему или безопасность.

5. Зачем validate и normalize:
   первый отклоняет некорректный смысл/структуру, второй приводит принятые данные
   к безопасным рабочим пределам.

6. Зачем retry:
   дать модели исправить формат с использованием конкретной ошибки.

7. Зачем fallback:
   сохранить работоспособность игры после исчерпания попыток; это не успех LLM.

8. Почему нет фриза:
   модель работает в отдельном executor, результат применяется через enqueue().

9. Как создаются режимы:
   Applier вызывает реализованные builders/controllers по белому списку типов.

10. Как предотвращаются остатки режима:
    единый cleanup останавливает состояние и удаляет сцену, physics, listeners,
    таймеры и ссылки.

11. Как оценивалось качество:
    серия запросов, latency, tokens/sec, success по попыткам, fallback rate, RAM.

12. Ограничения:
    ограниченный набор шаблонов, возможная долгая генерация, несовершенный JSON,
    простые визуальные объекты и простой football без полноценных AI-команд.

Не преувеличивай:
Не «LLM создаёт любую игру», а «LLM генерирует проверяемые параметры для
заранее реализованных игровых шаблонов».

13. ПОРЯДОК ИЗУЧЕНИЯ ПО 14-ДНЕВНОМУ ПЛАНУ

14. ИСТОЧНИКИ — ТОЛЬКО ДЛЯ НУЖНЫХ ЗАДАЧ
============================================================

Ниже приоритет отдан официальной документации и Javadoc. Для быстрого выполнения
не нужно читать каждый сайт целиком: указано, какой раздел открыть и зачем.

A. JAVA 21 И МНОГОПОТОЧНОСТЬ

1. Java 21 API — ExecutorService
https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ExecutorService.html
Читать: submit/execute, shutdown/shutdownNow, жизненный цикл executor.
Для чего: правильно владеть llmExecutor и закрывать его в destroy().

2. Java 21 API — CompletableFuture
https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/CompletableFuture.html
Читать: supplyAsync, runAsync, whenComplete, исключения при асинхронном выполнении.
Для чего: понять текущий Main и почему callback не равен render-потоку.

3. Java 21 API — java.lang.Float
https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Float.html
Читать: isFinite, isNaN, isInfinite.
Для чего: закрыть риск NaN/Infinity в GameModeSpec.

4. Java 21 API — java.nio.file.Path и Files
https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/file/Path.html
https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/file/Files.html
Читать: Path.of, resolve, normalize, toAbsolutePath, isDirectory, exists.
Для чего: проверка phi.model.dir и genai_config.json.

5. Java MOOC — только при пробелах в базовой Java
https://java-programming.mooc.fi/
Читать выборочно: classes/objects, interfaces, lists, exceptions.
Для чего: восполнить базу, если существующий код пока трудно читать.
Не проходить курс целиком вместо реализации проекта.

============================================================

Ты готов реализовать и защитить проект, если можешь без подсказки:

[ ] Нарисовать pipeline от запроса до modeNode.
[ ] Объяснить разницу Mock, retry и fallback.
[ ] Показать, какой код выполняется в llmExecutor, а какой в render-потоке.
[ ] Объяснить, почему whenComplete требует enqueue перед apply/HUD.
[ ] Прочитать GameModeSpec и назвать его игровые последствия.
[ ] Объяснить validate отдельно от normalize.
[ ] Написать FakeLlmClient для теста текущих двух попыток.
[ ] Написать тест на скобки внутри JSON-строки.
[ ] Объяснить NaN и Float.isFinite.
[ ] Реализовать движение speed * tpf и cooldown без Thread.sleep().
[ ] Реализовать pickup с active=false и защитой от двойного счёта.
[ ] Объяснить состояние RUNNING/WON/LOST и однократное завершение.
[ ] Перечислить всё, что cleanup удаляет кроме modeNode.
[ ] Объяснить Model, Tokenizer, GeneratorParams, Generator, TokenizerStream.
[ ] Объяснить max_length против лимита новых токенов.
[ ] Посчитать tokens/sec и JSON success rate без включения fallback в успех LLM.
[ ] Запустить тесты и сборку командами, задокументированными в README.
[ ] Назвать реальные ограничения проекта без преувеличения возможностей LLM.

Не требуется для этой курсовой:
- обучать или дообучать Phi;
- знать математику transformer на уровне реализации;
- писать собственный tokenizer/KV-cache;
- изучать весь jMonkeyEngine;
- строить сложный UI, NavMesh или AI футболистов;
- делать красивые GLB до завершения механики;
- читать все источники целиком.

Главный ориентир:
Каждую тему изучай ровно до момента, когда можешь применить её в текущем
маленьком шаге, проверить результат и объяснить, что произошло.

LLM предлагает параметры. Java проверяет. jME строит. Игрок играет.
