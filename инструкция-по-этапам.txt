Назначение документа:
Пошаговая инструкция для самостоятельной реализации проекта GameAI —
Java-игры на jMonkeyEngine, где NPC через локальную Phi-3.5-mini генерирует
игровые режимы по текстовому запросу игрока.

Главное правило:
Не переходи к следующему этапу, пока не выполнена проверка предыдущего.
Код добавляй небольшими частями:
изменил -> скомпилировал -> запустил -> проверил лог -> написал/обновил тест.

Важно:
Некоторые классы из инструкции ещё не существуют — их нужно будет создать.
LLM нельзя вызывать в render-потоке jME.
Сцену, HUD, input и physics изменяй только в render-потоке.
Ответ LLM всегда недоверенный: parse -> validate -> normalize -> apply.

7. СДЕЛАЙ FallbackGameModeFactory

Создай класс, который вручную собирает безопасный GameModeSpec:

public final class FallbackGameModeFactory {

    public GameModeSpec create() {
        GameModeSpec spec = new GameModeSpec();
        spec.name = "Fallback Collect";
        spec.description = "Резервный режим сбора предметов";
        spec.objective.type = "collect";
        spec.objective.targetCount = 3;
        spec.objective.timeLimitSec = 120;

        GameModeSpec.Spawn items = new GameModeSpec.Spawn();
        items.type = "item";
        items.count = 3;
        items.position = new float[]{0, 1, -3};

        spec.spawns.add(items);
        return spec.normalize();
    }
}

Это не Mock и не нейросеть. Это аварийный режим, который должен работать
всегда, даже если модель не загрузилась.

В Main.startGeneration():
1. При ошибке генерации лови исключение.
2. Пиши подробную ошибку в консоль.
3. Создавай fallback.
4. Применяй его через enqueue().
5. Обязательно сбрасывай generating = false.

Позже HUD должен показывать:

«Не удалось сгенерировать режим. Запущен резервный режим».

Не выдавай fallback за успешный ответ Phi.

поле подготовлено для будущего режима, но не считается реализованной функцией.

5. СДЕЛАЙ SpawnFactory

Вынеси создание кубов из GameModeApplier.

Пример метода:

Spatial create(GameModeSpec.Spawn spawn)

По типу:
- enemy — красный;
- item — зелёный;
- checkpoint — бирюзовый;
- trap — оранжевый.

Сохраняй не только Spatial, но и данные:

class SpawnedEntity {
    Spatial spatial;
    String type;
    float speed;
    float damage;
    boolean active;
}

Это пригодится для врагов, предметов, очистки и игровой логики.

6. СДЕЛАЙ CleanupService

При смене режима:
1. Останови игровой цикл старого режима.
2. Удали enemy/item controllers.
3. Удали физические тела, если они есть.
4. Отпиши слушатели.
5. Очисти таймеры и delayed actions.
6. Вызови modeNode.detachAllChildren().
7. Сбрось HUD.
8. Сбрось погоду.
9. Сбрось временные эффекты и ссылки на старые entity.

Простого detachAllChildren() для будущей физики будет недостаточно.

КРИТЕРИЙ ЗАВЕРШЕНИЯ ЭТАПА 3

Применяй по очереди:

night + fog + slow player
day + clear + fast player
sunset + rain

После каждого режима не должно оставаться старого тумана, дождя,
параметров игрока или объектов предыдущего режима.

============================================================
ЭТАП 4. SURVIVAL И COLLECT
============================================================

ЦЕЛЬ

Получить первые два режима, которые можно выиграть или проиграть.

1. СОЗДАЙ ИГРОВОЕ СОСТОЯНИЕ

enum GameState {
    READY,
    RUNNING,
    WON,
    LOST
}

GameSession или ObjectiveController должен хранить:
- текущий GameModeSpec;
- оставшееся время;
- текущий счёт;
- состояние;
- ссылку на игрока;
- списки врагов/предметов;
- список отложенных действий.

После WON или LOST прекращай:
- урон;
- движение врагов;
- изменение счёта;
- повторную обработку завершения;
- старые таймеры.

2. РЕАЛИЗУЙ EnemyController

Для простого survival:

если режим RUNNING:
    направление = позиция игрока - позиция врага
    обнулить Y
    нормализовать
    переместить врага на speed * tpf

Добавь:
- минимальную дистанцию атаки;
- cooldown, например 1 секунду;
- урон из spawn.damage;
- запрет движения сквозь границы арены;
- проверку active и состояния RUNNING.

Не используй отдельный поток на каждого врага.
Все враги обновляются в simpleUpdate(tpf).

3. РЕАЛИЗУЙ ЗДОРОВЬЕ И СМЕРТЬ

PlayerController.damage(amount):
1. Уменьшает здоровье.
2. Обновляет HUD.
3. Не позволяет здоровью стать меньше нуля.
4. При нуле отправляет событие onPlayerDeath.
5. Не обрабатывает повторную смерть, если игрок уже мёртв.

RuleEngine смотрит правила спеки:
- respawn — вернуть игрока на старт с задержкой;
- endLose — завершить режим поражением;
- healPlayer — восстановить здоровье;
- spawnWave — создать новую группу врагов.

Для задержек используй список задач с remainingSec, обновляемый через tpf.
Не используй Thread.sleep().

4. РЕАЛИЗУЙ SURVIVAL

Условия:

старт -> RUNNING
здоровье = 0 -> LOST или respawn по правилам
таймер = 0 -> WON

HUD:

Выживите: 87 сек.
Здоровье: 64/100

Проверь:
- враги действительно приближаются;
- урон наносится не каждый кадр;
- победа наступает один раз;
- смерть не приводит к двойному завершению;
- после рестарта здоровье и таймер сбрасываются;
- старые враги не атакуют в новом режиме.

5. РЕАЛИЗУЙ COLLECT

Для каждого активного предмета:

if (playerPosition.distanceSquared(itemPosition) < pickupRadiusSquared) {
    // собрать
}

При сборе:
1. Пометь предмет неактивным.
2. Удали его со сцены.
3. Увеличь счёт ровно на 1.
4. Обнови HUD.
5. Проверь достижение цели.

Условия:

score >= targetCount -> WON
timeLimitSec истёк -> LOST

Поле active важно, чтобы один предмет нельзя было собрать дважды
за соседние кадры.

6. УЛУЧШИ MockLocalLlm

Сделай минимум три заранее подготовленных ответа:
- survival;
- collect;
- тестовый неправильный ответ для отладки.

Для разработки Mock может выбирать JSON по понятному признаку запроса.
Это не «имитация интеллекта», а детерминированный инструмент тестирования.

7. ПРОВЕРЬ ПЕРЕКЛЮЧЕНИЯ

Выполни 20 переключений survival <-> collect.

Не должно быть:
- предметов и врагов от предыдущего режима;
- урона после завершения режима;
- старого таймера в HUD;
- старых delayed actions;
- лишних input listeners;
- роста количества объектов после каждого переключения.

КРИТЕРИЙ ЗАВЕРШЕНИЯ ЭТАПА 4

Survival и collect имеют начало, игровой процесс, победу/поражение
и корректный повторный запуск.

============================================================
ЭТАП 5. FOOTBALL
============================================================

ЦЕЛЬ

Добавить третий режим и доказать, что архитектура подходит
не только для врагов.

1. РАСШИРЬ GameModeSpec

Добавляй только необходимое:

public static class Scoring {
    public int winScore = 3;
    public int pointsPerGoal = 1;
}

public Scoring scoring = new Scoring();

Добавь:

objective.type = score
spawn.type = ball
spawn.type = goal

Обнови одновременно:
- SUPPORTED_OBJECTIVE_TYPES;
- SUPPORTED_SPAWN_TYPES;
- SYSTEM_PROMPT;
- validator;
- normalize;
- Mock JSON;
- SpawnFactory.

Если добавить значения только в prompt, LLM сможет прислать режим,
который игра не умеет строить.

2. ПОДКЛЮЧИ ФИЗИКУ

Для мяча можно использовать Bullet:

<dependency>
    <groupId>org.jmonkeyengine</groupId>
    <artifactId>jme3-bullet</artifactId>
    <version>${jme.version}</version>
</dependency>
<dependency>
    <groupId>org.jmonkeyengine</groupId>
    <artifactId>jme3-bullet-native</artifactId>
    <version>${jme.version}</version>
</dependency>

В приложении:

BulletAppState bulletAppState = new BulletAppState();
stateManager.attach(bulletAppState);

Для мяча:
- SphereCollisionShape;
- RigidBodyControl;
- масса больше нуля;
- физический объект добавляется в PhysicsSpace.

Для игрока можно:
- перейти на BetterCharacterControl;
- либо оставить простой контроллер и передавать мячу импульс при контакте.

Второй вариант проще, но менее реалистичен. Для MVP выбирай решение,
которое сможешь стабилизировать и объяснить.

3. СДЕЛАЙ ПОЛЕ И ВОРОТА

Поле:
- прямоугольная платформа;
- боковые границы;
- две ворота на противоположных сторонах.

Для первой версии гол можно определять без collision listener:

мяч находится внутри прямоугольной области ворот
и гол ещё не был засчитан в текущем эпизоде.

После гола:
1. Увеличь счёт.
2. Обнови HUD.
3. Проверь winScore.
4. Если матч продолжается — верни мяч в центр.
5. Сбрось линейную и угловую скорость.
6. На короткое время запрети повторный гол.

4. ЗАВЕРШЕНИЕ МАТЧА

Например:

счёт >= winScore -> WON
время вышло -> сравнить счёт или завершить по правилам режима

Для MVP можно сделать одного игрока против пустых ворот с целью забить
N мячей. Не добавляй сложный AI футболистов — это отдельный большой проект.

5. ОЧИСТКА ФИЗИКИ

При смене режима явно удали:
- мяч из PhysicsSpace;
- границы;
- ворота;
- collision listeners;
- controls;
- спортивный HUD;
- ссылки на старое физическое состояние.

КРИТЕРИЙ ЗАВЕРШЕНИЯ ЭТАПА 5

- Мяч не проваливается сквозь пол.
- Игрок может его толкать.
- Один эпизод не засчитывает десять голов подряд.
- После гола мяч корректно возвращается.
- Survival после football запускается без старого мяча и физических тел.

ЭТАП 6. ПОДКЛЮЧЕНИЕ GLB-МОДЕЛЕЙ
============================================================

ЦЕЛЬ

Заменить кубы моделями, не ломая игровую логику.

1. ПОДГОТОВЬ СТРУКТУРУ

src/main/resources/assets/Models/enemy.glb
src/main/resources/assets/Models/item.glb
src/main/resources/assets/Models/checkpoint.glb
src/main/resources/assets/Models/trap.glb
src/main/resources/assets/Models/ball.glb
src/main/resources/assets/Models/goal.glb

Не обязательно создавать все модели сразу. Начни с item.glb.

2. СДЕЛАЙ БЕЛЫЙ СПИСОК

Map<String, String> MODEL_PATHS = Map.of(
    "enemy", "Models/enemy.glb",
    "item", "Models/item.glb"
);

LLM возвращает только "item". Она никогда не возвращает путь к файлу.

Это защищает от:
- произвольных путей;
- отсутствующих ресурсов;
- загрузки непредусмотренных моделей.

3. КЭШИРУЙ ПРОТОТИПЫ

Не вызывай loadModel() для каждого экземпляра.

Алгоритм:

тип уже загружен -> clone()
тип не загружен -> loadModel() -> сохранить прототип -> clone()
файл отсутствует -> куб

Материалы прототипов не изменяй, если они общие.
Если нужен отдельный цвет каждому экземпляру — создавай отдельный материал.

4. НАСТРОЙ РАЗМЕР И ПОЛОЖЕНИЕ

Для каждой модели могут понадобиться:

scale
yOffset
rotation

Это параметры ассета, а не значения от LLM.

Проверь:
- модель стоит на полу;
- не слишком большая;
- повёрнута правильно;
- не чёрная благодаря уже добавленному свету;
- pivot не заставляет объект проваливаться под пол.

5. СОХРАНИ FALLBACK

Если загрузка GLB выбрасывает исключение:
1. Запиши ошибку.
2. Создай куб того же типа.
3. Продолжи режим.

КРИТЕРИЙ ЗАВЕРШЕНИЯ ЭТАПА 6

- 20 предметов не вызывают 20 загрузок с диска.
- Отсутствующий файл не роняет игру.
- Смена режима удаляет все экземпляры.
- Логика столкновений не зависит от визуальной модели.

ЭТАП 7. МЕТРИКИ РЕАЛЬНОЙ PHI И СТАБИЛЬНОСТЬ
============================================================

ЦЕЛЬ

Получить факты для курсовой: скорость, надёжность и ограничения системы.

1. ДОБАВЬ ИЗМЕРЕНИЯ

Используй:

long start = System.nanoTime();
// операция
long elapsedMs = (System.nanoTime() - start) / 1_000_000;

Измеряй отдельно:
- загрузку модели;
- полный запрос;
- каждую попытку;
- парсинг и валидацию;
- применение режима.

Не смешивай загрузку модели с временем первой генерации —
это разные операции.

2. СЧИТАЙ ТОКЕНЫ

В OnnxGenAiPhiClient количество итераций generateNextToken() —
это количество сгенерированных токенов.

Можно создать объект результата:

class GenerationResult {
    String text;
    int generatedTokens;
    long generationTimeMs;
}

Тогда:

tokens/sec = generatedTokens / (generationTimeMs / 1000.0)

Не считай кусочки текста onPiece токенами: один токен не всегда
соответствует одному видимому фрагменту.

3. ПОДГОТОВЬ НАБОР ЗАПРОСОВ

Минимум 10–20:
- выживание ночью;
- сбор предметов при дожде;
- футбол;
- неполный запрос;
- противоречивый запрос;
- очень длинный запрос;
- просьба добавить неподдерживаемую сущность;
- просьба вернуть текст вместо JSON;
- экстремальные значения скорости/здоровья;
- повтор одного запроса несколько раз.

4. СОХРАНЯЙ РЕЗУЛЬТАТЫ В CSV

Колонки:

requestId
clientType
attempts
generationMs
generatedTokens
tokensPerSec
parseSuccess
validationSuccess
fallbackUsed
error

Полезные итоговые показатели:

JSON success rate =
число успешно провалидированных ответов / общее число запросов

Fallback rate =
число fallback / общее число запросов

RAM измеряй через диспетчер задач, VisualVM или другой внешний инструмент.
Память нативной ONNX-модели не всегда корректно видна через обычный Java heap.

5. ПРОВЕРЬ СТАБИЛЬНОСТЬ

Выполни подряд:
- 5–10 запросов;
- несколько смен режимов;
- намеренно неправильный ответ;
- fallback;
- повторную успешную генерацию;
- закрытие приложения.

Проверь, что после ошибки можно продолжать работу.

6. ТОЛЬКО ТЕПЕРЬ ОПТИМИЗИРУЙ

Если замеры показывают необходимость:
- добавь warm-up;
- сократи prompt;

При кэшировании не возвращай один и тот же изменяемый GameModeSpec
разным режимам. Сохраняй JSON или создавай копию.
