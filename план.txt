ПЛАН ПРОЕКТА GameAI
Актуализирован: 23.11.2026 по текущему состоянию исходников и подтверждённым запускам.
Основной журнал ежедневного прогресса: план-на-2-недели-по-5-часов.txt.

Цель: Java-игра на jMonkeyEngine, в которой игрок через NPC отправляет
текстовый запрос локальной Phi-3.5-mini, получает игровой режим и может в него играть.

Главная рамка проекта:
- Нейросеть НЕ управляет сценой, физикой или памятью игры напрямую.
- Нейросеть возвращает только JSON-описание режима GameModeSpec.
- Ответ модели всегда недоверенный: parse -> validate -> normalize -> apply.
- Java строит режим только из поддерживаемых шаблонов и безопасных параметров.
- Генерация асинхронная: запрос -> NPC думает -> загрузка -> режим готов.
- generate() нельзя вызывать в render-потоке jME; изменения сцены — только в нём.
- Старый режим полностью очищается перед применением нового.

Обозначения:
[ГОТОВО]      — соответствующий код уже есть.
[ЧАСТИЧНО]    — основа есть, но функция ещё не закончена или не проверена полностью.
[НЕ СДЕЛАНО]  — нужно реализовать.
[ПОЗЖЕ]       — расширение после MVP, сейчас не отвлекаться.

1. ЧТО УЖЕ ЕСТЬ В ПРОЕКТЕ
============================================================

[ГОТОВО] Базовое приложение Main.Main:
- SimpleApplication, пол, камера, DirectionalLight и AmbientLight.
- Выбор LLM через -Dgameai.llm=mock|onnx; по умолчанию используется mock.
- Путь к модели настраивается через -Dphi.model.dir=...
- Отдельный однопоточный ExecutorService для загрузки и генерации.
- Флаги modelReady и generating не дают запустить генерацию до загрузки
  или запустить несколько генераций одновременно.
- Применение результата возвращается в render-поток через enqueue().
- Ресурсы клиента и executor освобождаются в destroy().
- setPauseOnLostFocus(false) отключает паузу jME при потере фокуса.
- Измеряются loadMs и полный generationMs, включая возможный retry.

[ГОТОВО] Клиенты LLM:
- LLM.LocalLlmClient — общий интерфейс load/generate/isReady/close.
- LLM.MockLocalLlm — разработка без реальной модели.
- LLM.OnnxGenAiPhiClient — Phi через ONNX Runtime GenAI.
- maxNewTokens = 768, temperature = 0, очистка служебных токенов,
  потоковое декодирование и освобождение нативных ресурсов.
- LLM.llmtest.OnnxSmokeTest — отдельная точка для проверки реальной модели.

[ГОТОВО] JSON-pipeline:
- GameModeGenerator содержит system prompt с полным валидным JSON-образцом
  и chat template Phi.
- MAX_ATTEMPTS = 2; при ошибке модель получает предыдущий ответ,
  конкретную ошибку и исходный запрос.
- Из ответа извлекается один сбалансированный JSON-объект.
- Jackson преобразует JSON в GameModeSpec.
- GameModeSpecValidator отсекает пустой {}, неверные enum/диапазоны,
  пустые name/spawns и другие ошибки. Пустое description разрешено
  и безопасно заполняется в normalize().
- GameModeSpec.normalize() ограничивает числа, списки и координаты,
  удаляет неподдерживаемые spawn/rules и подставляет значения по умолчанию.
- Полный rawResponse и извлечённый JSON сейчас выводятся в консоль.

[ГОТОВО] Базовый GameModeApplier:
- Отдельный modeNode для объектов сгенерированного режима.
- Очистка предыдущего режима через detachAllChildren().
- Спавн кубов-заглушек: enemy/item/checkpoint/trap.
- Цвета кубов различаются по типу.

3. ТЕХНОЛОГИЧЕСКИЕ РЕШЕНИЯ — ЗАФИКСИРОВАТЬ И НЕ МЕТАТЬСЯ
============================================================

Для курсовой остаётся связка:
Java 21 + jMonkeyEngine + Jackson + ONNX Runtime GenAI + локальная Phi-3.5-mini.

DL4J в проект добавлять не нужно:
- DL4J полезен для построения, обучения и дообучения сетей на JVM.
- Текущая задача — только локальный инференс готовой LLM.
- ONNX Runtime GenAI уже предоставляет токенизацию, цикл генерации,
  KV-cache и поддержку Phi без самостоятельной реализации этих механизмов.
- В пояснительной записке DL4J можно упомянуть как более общий аналог,
  а выбор ONNX Runtime GenAI обосновать специализацией под генеративные модели.

MCP также не нужен: игра локальная, клиент встроен прямо в приложение.

Не проводить сейчас массовый рефакторинг пакетов ради красоты.
Существующие Main, LLM и LLM.GameMode оставить до стабильного MVP;
новые классы можно размещать в понятных подпакетах внутри текущей структуры.

4. ТЕКУЩАЯ И ЦЕЛЕВАЯ АРХИТЕКТУРА
============================================================

Уже реализованная цепочка:
Клавиша 1/2 в Main
-> GameModeGenerator
-> LocalLlmClient (Mock или ONNX)
-> извлечение JSON
-> Jackson -> GameModeSpec
-> GameModeSpecValidator
-> normalize()
-> GameModeApplier
-> кубы на сцене.

Целевая цепочка MVP:
Игрок подходит к NPC и нажимает E
-> NpcInteractionController
-> поле ввода запроса
-> Main/AsyncLlmService
-> GameModeGenerator
-> LocalLlmClient
-> JsonExtractor
-> Jackson -> GameModeSpec
-> GameModeSpecValidator
-> normalize()
-> GameModeApplier/LevelBuilder
-> WorldApplier + SpawnFactory
-> PlayerController + ObjectiveController + RuleEngine
-> HUD с состоянием, целью, таймером и результатом.

При ошибке:
загрузка/генерация/парсинг/валидация не удалась
-> понятное сообщение в HUD
-> FallbackGameModeFactory
-> безопасный локальный режим без участия LLM.

Минимально необходимые новые компоненты:
- npc/NpcInteractionController — радиус, E, открытие ввода, реплики.
- ui/HudController — статусы, таймер, цель, счёт, ошибки.
- ui/PromptInputController — ввод и отправка запроса.
- game/PlayerController — перемещение и взаимодействие с миром.
- game/WorldApplier — свет, время суток, туман/дождь, параметры мира.
- game/SpawnFactory — создание поддерживаемых сущностей.
- game/ObjectiveController — survive/collect/score/reach по мере добавления.
- game/RuleEngine — события и действия из spec.rules.
- game/CleanupService — объекты, controls, listeners, физика и состояние.
- llm/JsonExtractor — отдельно и с unit-тестами.
- llm/FallbackGameModeFactory — встроенный безопасный GameModeSpec.
- test/... — тесты extractor/validator/normalizer/retry/fallback.

Не создавать все классы заранее пустыми. Вводить их по мере появления
реальной ответственности, сохраняя маленькие проверяемые изменения.

5. ТОЧНЫЙ ОБЪЁМ MVP
============================================================

MVP состоит не из «кубов по JSON», а из трёх мини-режимов с началом,
целью и завершением:

1. Survival:
- арена и управляемый игрок;
- враги хотя бы с простым преследованием;
- здоровье игрока и урон;
- таймер выживания;
- победа по истечении времени, поражение при смерти.

2. Collect adventure:
- предметы на арене;
- сбор при касании;
- счётчик «собрано/нужно»;
- победа после сбора цели, при наличии лимита — поражение по времени.

3. Football:
- поле, мяч и две зоны ворот;
- взаимодействие игрока с мячом;
- счёт и ограничение по времени или до нужного числа голов;
- корректный сброс мяча после гола и при смене режима.

Fallback:
- один простой встроенный collect-режим;
- создаётся локально даже при неработающей модели;
- явно помечается в HUD как резервный, чтобы не выдавать его за ответ Phi.

После MVP можно добавлять defend/race/puzzle/sandbox, boss, escort,
сложные диалоги, звук, партиклы и красивые модели. До MVP — нет.

7. СХЕМА GameModeSpec: РАЗВИВАТЬ ПОСТЕПЕННО
============================================================

Сейчас поддерживаются:
- world: gravityY, timeOfDay=day/night/sunset, weather=clear/rain/fog;
- player: moveSpeed, jumpForce, maxHealth;
- objective: survive/collect/reach/defend, targetCount, timeLimitSec;
- spawns: enemy/item/checkpoint/trap, position/count/speed/damage;
- rules: onPlayerDeath/onObjectiveComplete/onTimeExpired/onScoreChanged;
- actions: respawn/endWin/endLose/spawnWave/healPlayer;
- name, description, difficulty, schemaVersion.

Для football при необходимости добавить:
- objective.type=score;
- spawn.type=ball/goal;
- scoring.winScore, pointsPerGoal;
- корректную валидацию и нормализацию этих полей.

Для воспроизводимости после MVP:
- seed, чтобы одинаковые spec+seed давали одинаковый layout;
- arenaRadius/maxEntities как ограничения построителя, а не свободу для LLM.

Только после MVP:
- modeCategory, fogDensity, skyPreset, цвета света;
- race/escort/solve, switch/door/vehicle;
- dialogue, feedback, particles, cameraShake.

Правило: сначала механика и тест, потом новое значение в prompt/schema.
Нельзя добавлять в system prompt обещания, которые Applier не умеет выполнять.

============================================================
9. ОСНОВНЫЕ РИСКИ
============================================================

1. Phi возвращает нестабильный JSON.
Закрытие: strict prompt, temperature=0, extractor, validator, normalize,
2 попытки, fallback и метрика success rate.

2. Генерация слишком долгая.
Закрытие: короткий prompt/output, maxNewTokens=768, фоновая загрузка,
HUD ожидания, готовые демо-запросы; кэш/warm-up после профилирования.

3. Падения и утечки при смене режима.
Закрытие: один владелец состояния режима, CleanupService, удаление controls
и physics до detach, отписка listeners, повторный тест переключений.

4. Race condition между фоном и jME.
Закрытие: LLM только в llmExecutor; rootNode/input/scene только в render-потоке;
состояние generation явно отображать в HUD.

5. Scope разрастается.
Закрытие: сначала survival + collect + football; расширения только после MVP.

6. ONNX/DLL не запускаются на другом компьютере.
Закрытие: точные версии, README, проверка чистого запуска, mock/fallback,
раздел troubleshooting. Модель не включать в git.

7. Красивые обещания в курсовой не совпадают с реализацией.
Закрытие: формулировка «асинхронная генерация параметров игрового режима
локальной LLM с валидацией, fallback и построением уровня из шаблонов».
Не обещать мгновенную генерацию или произвольные уровни любой сложности.

============================================================
10. КРИТЕРИИ ГОТОВНОСТИ
============================================================

MVP готов, если одновременно выполнено:
- игра запускается и есть управляемый игрок;
- запрос вводится у NPC внутри игры;
- модель загружается один раз, генерация не блокирует render-поток;
- ответ проходит parse -> validate -> normalize -> apply;
- невалидный JSON отклоняется, ошибка видна, после сбоя работает fallback;
- world/player/spawns реально применяются, а не только хранятся в DTO;
- survival, collect adventure и football играбельны и имеют win/lose;
- старый режим полностью очищается;
- mock и реальная Phi различаются в настройках и логах;
- есть автоматические тесты JSON/validator/normalize/retry/fallback;
- README позволяет повторить запуск.

Хорошая защита дополнительно включает:
- таблицу метрик реальной Phi;
- демонстрацию боевого и мирного режима;
- демонстрацию битого JSON и fallback;
- повторные смены режимов без утечек;
- объяснение, почему LLM не управляет движком напрямую;
- сравнение специализированного ONNX Runtime GenAI с более общим DL4J;
- ограничения и дальнейшее развитие без преувеличений.
